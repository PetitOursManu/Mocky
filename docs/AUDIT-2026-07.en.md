# Mocky action plan — multi-agent audit, synthesis and roadmap

**English** · [Français](AUDIT-2026-07.md)

> **Why it works this way —** An audit that merely lists defects never turns into work: you have to know where to start. So the document is organised into batches — one batch = one theme, one costed effort, one declared regression risk — because that is the unit you can ship, test, and abandon wholesale if it goes wrong. Every finding carries its `file:line` path so that verification does not depend on how much trust you place in the report.

> Basis: 5 dimension audits + adversarial verification of the security findings. Every finding below has been re-read in the code (paths and lines verified). No file was modified.

## 0. Verdict on one page

> **Why it works this way —** A report of sixty findings becomes unreadable if everything in it looks equally serious. This page first settles what works, then names the three problems that govern all the others, and explicitly files the rest under "cosmetic": the hierarchy is the deliverable, not the list. It opens with the successes because an audit that lists nothing but defects loses all sense of what must on no account be broken while fixing them.

Mocky **does what it promises**: a genuine infinite canvas, streaming generation, Interact mode, links + Demo, 17 presets, snip annotations, runnable Vite ZIP export, accounts + SSO, a complete server-side Muse pipeline. The build is green (`tsc --noEmit` = 0, 398 tests in 3.3 s), the typing is strict (strict + noUnused*, zero `@ts-ignore`), and the authentication foundation is sound (scrypt + salt, `timingSafeEqual`, 32-byte tokens, HS256 verified in constant time with `iss`/`aud`/`exp`/anti-replay `jti`).

The three real problems are not where you would expect them:

| # | Problem | Why this is the real issue |
|---|---|---|
| **1** | **The persistence layer loses work** | `src/lib/sync.ts` (86 lines, **zero tests**) and `src/lib/project.ts` contain 4 reproducible paths to losing projects. You are the user here: this is risk no. 1 for you personally, ahead of any security question. |
| **2** | **The whole expensive backend surface is open with no authentication** | `/__provider`, `/api/images/*`, `/api/muse/dossier`, `/api/text/vision`: 4 mounts with no guard. **What is cosmetic, and which I own as such** (do not prioritise): `public/` copied needlessly into the Docker image, `react`/`react-dom` in `dependencies`, the missing `allow=""` attribute on the iframe (not exploitable as things stand, verified), the scrypt password policy, the HSTS/CSP headers on the main document. ## 1. BATCH 0 — Stop losing work *(BUG — absolute priority)*

> **Why it works this way —** The two batches marked "RISK" that follow presuppose a third party: an attacker, a network or a browser has to play along before any damage occurs. This one describes a loss already under way, borne by the person using the tool with nobody else involved, and data loss is the only damage no later fix can undo. Hence the absolute priority, independent of any question of network exposure.

This is the only batch where **you are the victim**, not some hypothetical attacker. Four independent paths, all inside 450 untested lines.

### 0.1 `reconcileOnLogin` overwrites local with the server without comparing dates *(critical)*

> **Why it works this way —** As soon as the same data exists in two copies — the browser and the server — reconciliation needs a criterion to settle between them; without one, it guesses. The implicit rule here is "the server wins", which destroys the local copy every time the local copy is the more recent one, that is, every time a tab closed before the deferred upload could leave. Yet the timestamp needed to arbitrate is already written by the server: it is the client's TypeScript type that fails to declare it, so the field is silently dropped on read.

`src/lib/sync.ts:72-86` — verified: `hasServerProjects` is true as soon as the server blob is neither `null` nor `'[]'`, then `localStorage.setItem(PROJECTS_KEY, server.projects)` **with no arbitration at all**. The `Project.updatedAt` field exists (`src/lib/project.ts:52`), the server already writes `updatedAt: Date.now()` (`server/index.js:608`), but `interface ServerData` (`src/lib/api.ts:24-27`) **does not even declare it** — it is thrown away by the client.

Reproducible scenario: I generate a screen, I close the tab within the second. The localStorage flush goes through (`project.ts:89`, `beforeunload`), the 800 ms server push (`sync.ts:38`) does not. I reopen: `App.tsx:49` calls `reconcileOnLogin`, the server returns the earlier blob, `localStorage` is overwritten, `changed` is true, `App.tsx:50` runs `window.location.reload()`. **The screen is gone, without a word.**

**Fix** (`src/lib/api.ts`, `src/lib/sync.ts`, `server/index.js:598-602`):
1. Add `updatedAt?: number` to `ServerData` and stop discarding it on the server side.
2. In `reconcileOnLogin`, compute `localMax = max(p.updatedAt)` and adopt the server copy only if it is **strictly more recent**.
3. Where both sides have diverged, merge by `project.id` keeping the more recent one — **never delete a local project that is absent from the server**.
4. `navigator.sendBeacon('/api/data', blob)` in the `beforeunload` of `project.ts:89` to close the 800 ms window.

### 0.2 `pushNow` swallows writes made during an in-flight push *(critical)*

> **Why it works this way —** Merging several upload requests into one is correct: there is no point writing the same content five times. But merging is only safe if the upload re-reads the data at the moment it leaves; here the read happens once, before the retry loop, so everything written during the fifteen seconds of retries falls outside the snapshot that gets sent. Nothing records "something happened in the meantime", and that is exactly the one piece of information that would be needed to fire another upload.

`src/lib/sync.ts:36` — verified: `if (pending) return pending // already in flight — coalesce`. And `doPushWithRetry` (`sync.ts:44-45`) reads `localStorage` **once only, before the retry loop**, then retries 5 times with 1+2+4+8 s backoff ≈ 15 s. During that window, every `scheduleSync()` returns immediately, and at the end `pending = null` without any `dirty` flag re-triggering anything.

Combined with 0.1, the loop closes: the server keeps a stale version, then forces it back onto the local copy at the next start-up.

**Fix** (~10 lines in `src/lib/sync.ts`): add `let dirty = false`; have `scheduleSync()` set it; move the localStorage read **inside** the `while` loop; in the `finally` of `pushNow`, after `pending = null`, do `if (dirty) { dirty = false; return pushNow() }`.

### 0.3 A sync failure is 100% silent *(major)*

> **Why it works this way —** An async function launched from a `setTimeout` no longer has a caller: nobody is awaiting its result, so its failure surfaces nowhere, except as an unhandled promise rejection. The channel meant to display it already exists in the module, but no component imports it, so thirty seconds of unsuccessful attempts look, from the user's side, exactly like a successful save. A silent failure is more dangerous than a noisy one, because it prevents the only useful reaction: redo the work, or copy it somewhere else.

`sync.ts:38`: `window.setTimeout(pushNow, 800)` — `pushNow` is `async` and throws `new Error('Sync failed after retries')` (`sync.ts:58`) **with no `.catch()` at all** → unhandled promise rejection. The `syncStatus()` function (`sync.ts:29-31`) was written for precisely this (the comment on line 24 says "lets the UI show a syncing… / sync failed indicator") but **it is imported nowhere**.

**Fix**: an explicit `.catch()` at the scheduling point; turn `syncStatus` into a small observable store (`subscribe(cb)` + `'idle'|'syncing'|'failed'`) rendered in the header of `src/App.tsx:180-201` next to the account button, with a "Retry" button; warn on `beforeunload` when the state is `'failed'`.

### 0.4 `localStorage.setItem` without `try/catch`: `QuotaExceededError` stops everything, permanently *(major)*

> **Why it works this way —** A browser's local storage has a finite size and refuses writes beyond it by throwing an exception. If nobody catches it, nothing further in the function runs: neither the reset of the pending queue nor the trigger for the server sync — so a single refused write severs both save paths at once, for the whole session. The threshold arrives all the sooner because each screen keeps two complete versions of its source code, doubling the footprint in exchange for a single level of undo.

`src/lib/project.ts:73` — `flushProjectsNow()` performs the `setItem` unprotected, called from a `setTimeout` (l.85) and from `beforeunload` (l.89): nobody catches. If it throws, `pendingProjects = null` (l.74) is never reached and neither is `scheduleSync()` (l.79). **Local saving AND server sync both stop, silently.** Your actual blob already weighs 209,684 bytes, and every screen stores `code` **AND** `previousCode` (`project.ts:26-28`) — the footprint is nearly doubled for nothing.

**Fix**: `try/catch` + reporting through the `syncStatus` channel with an actionable message; **remove `previousCode` from what is persisted** (keep it in an in-memory `Map<screenId,string>` inside ProjectView — it is only used by `onRevertScreen`, `ProjectView.tsx:292-301`) → footprint roughly halved for zero functional regression.

### 0.5 Two Mocky tabs overwrite each other *(major)*

> **Why it works this way —** Local storage is shared between all tabs of the same site, but it is not watched: each tab reads the project list once when it opens, keeps it in memory, then rewrites the entire list on every save. A tab that was never told about an addition made elsewhere therefore deletes it by writing its own version, then pushes that truncated version to the server. The browser does emit an event made for exactly this, addressed to other tabs only; it would be enough to listen for it, and nothing does.

Verified by grepping all of `src/`: **not one** occurrence of `addEventListener('storage'`, `BroadcastChannel`, `visibilitychange` or `pagehide`. Each tab loads the projects once on mount (`project.ts:220`) then rewrites the **whole** array on every flush (l.73). Tab A generates a screen; tab B moves a frame → its flush rewrites everything without A's screen, then pushes that truncated array to the server. Same pattern for DESIGN.md (`src/lib/design.ts:28-29`).

**Fix** (~15 lines): a `useEffect` in `useProjects` (`project.ts:219-224`) listening to `window.addEventListener('storage', …)` — the event is only emitted towards **other** tabs, which is exactly the behaviour wanted. Same in `design.ts`.

### 0.6 `reconcileOnLogin` runs twice per sign-in *(major)*

> **Why it works this way —** One and the same responsibility — reconciling local and server after sign-in — is written in two places, in the auth modal and in the root component. Two concurrent runs of the same exchange read and rewrite the same data without coordinating: the outcome then depends on the order in which the network responses arrive, and two page reloads race each other. The problem is not the cost of duplicate requests, it is that saving no longer has a single owner.

Verified: `src/components/AuthModal.tsx:47-51` does `enableSync(true)` + `await reconcileOnLogin()` + a conditional reload, and `src/App.tsx:276-284` (`onSignedIn`) **does exactly the same thing again**. Two concurrent `GET /api/data`, potentially two `PUT`, two reload paths racing.

**Fix**: delete the corresponding lines from `AuthModal.tsx` — the modal authenticates and calls `onSignedIn`, full stop. `App.tsx` remains the sole owner of reconciliation.

### 0.7 Safety net

> **Why it works this way —** The preceding fixes alter the path that writes your data, that is, the part of the code where a regression does not show up straight away and cannot be recovered from. So the tests are written first, against the exact scenarios that break, so that the fix is verifiable rather than merely plausible. To that is added a React error boundary, because an exception during render tears down the whole tree: without one, a single faulty line in a large component yields a blank page, with no message and no way back.

- **`src/lib/sync.test.ts`** (to be created): fake `api` + fake localStorage, 4 cases — server more recent, local more recent, writes during an in-flight push, retries exhausted.
- **`src/lib/project.test.ts`** (to be created): 300 ms debounce, flush on `beforeunload`, `setItem` throwing, `storage` event.
- **`src/components/ErrorBoundary.tsx`** (to be created, ~40 lines): `src/main.tsx:10` mounts `<App/>` **with no boundary at all** (the project's only one is injected *inside* the iframe, `Preview.tsx:167`). A render exception in `ProjectView.tsx` (1,624 lines, full of unguarded `screens.find(...)`, e.g. l.940 and l.410) = a mute blank page with no way back. Two levels: around `<App/>` (a "Reload" button) and around `<ProjectView/>` in `App.tsx:220-231` (a "Back to projects" button → `goHome()`), so that one corrupted project does not take the others with it.

**Batch 0 effort: 2–3 days. Regression risk: medium** (we are touching the persistence path — hence tests first).

## 2. BATCH 1 — Lock down the server *(RISK)*

> **Why it works this way —** The severity of this entire batch depends on a variable that is not in the code: is the instance reachable beyond its owner's machine. The same defect rates as "fix one day" on an isolated workstation and "fix before anything else" behind a public domain name, hence a section that opens with the decision rather than with the findings. It is placed first because a single line of configuration, the address the port is published on, tips you from one case to the other.

> **A prior decision, to be taken before opening this batch.** This whole section assumes the instance is reachable beyond your machine. `docker-compose.yml:16-17` publishes `"8787:8787"` on **all** interfaces, and `server/index.js:642` calls `app.listen(PORT)` with no bind address (so `0.0.0.0`).
> - **If Mocky stays on your PC / your trusted LAN** → this batch drops to priority 3, after the design. Do 1.1 and 1.2 anyway (30 minutes).
> - **If Mocky sits behind Caddy/Nginx and is reachable from the internet** → this batch comes **before everything else**, batch 0 included.
> A 2-minute fix in both cases: `ports: - "127.0.0.1:8787:8787"` in `docker-compose.yml:16-17`.

### 1.1 Four expensive routes with no authentication whatsoever *(critical)*

> **Why it works this way —** In Express, protecting a route is a matter of ordering: an identity check only applies to what is mounted after it. These four mounts come before the authentication function is even defined: this is therefore not a badly written check, it is the absence of one. What changes the nature of the problem, now that the administrator can place a model key on the server, is that these routes no longer merely give access to data: they spend the host's money, write files and delete them.

Middleware chain verified in `server/index.js`: `app` created at l.238, `cookieParser` l.239, security headers l.242-248 (no auth), then the mounts. `currentUser` is defined at l.286 and `requireAdmin` at l.306 — so **afterwards**, and they are never applied to the routes below:

| Route | Line | What an anonymous user can do |
|---|---|---|
| `/__provider` | `index.js:279` | Unlimited inference on the admin's LLM key. Worse for `kind: 'ollama'`: `dialect.js:127-137` builds `url = base + subpath` from `req.originalUrl` and `provider-proxy.js:174` preserves the method → `DELETE /__provider/api/delete` with `{"name":"..."}` (the `name` field escapes the `model` rewrite, l.150) deletes a model on the admin's Ollama. |
| `/api/text/vision` | `index.js:492` | **Read SSRF.** Verified line by line: when no admin provider is configured (the default state), `baseUrl` comes from the `x-provider-base` header (l.500) and `assertSafeTarget` **is never called** — unlike `provider-proxy.js:129-138` and `muse/llm.js:40`. `vision.js:104-113` returns up to 400 characters of the internal response body. A full LAN sweep plus `169.254.169.254` from the internet, with no account. |
| `/api/images/*` | `index.js:625` | `GET /library` exposes every prompt (= client briefs) and other people's `projects`; `library.zip` exfiltrates the lot; **`DELETE /:hash` performs an `fs.rmSync`** (`library.js:219`), with no trash. And the hashes are not a secret: `GET /library` lists them. A self-contained destruction chain. |
| `/api/muse/dossier` | `index.js:613` | Spends the admin provider's tokens (`muse/routes.js:52-58`, `trusted: true`). With `useFetch:true`, launches Chromium. |

**Fix** (~30 lines, `server/index.js`):
```
// before line 279
function requireUser(req, res, next) { const u = currentUser(req); if (!u) return res.status(401).json({error:'auth'}); req.user = u; next() }
```
- `/__provider`: refuse with 401 if `textConfig.target(profileFromRequest(req))` exists **and** `currentUser(req)` is null (browser-key mode can stay anonymous: it costs the host nothing).
- `app.use('/api/images', requireUser, images.router)` and `app.use('/api', requireUser, createMuseRouter(...))`.
- `DELETE /api/images/:hash` → `requireAdmin` (or the owner, see 1.4).
- `/api/text/vision` → `requireUser` **and** `assertSafeTarget(baseUrl + '/api/chat')` inside a try/catch before building `target` (`index.js:500-505`).
- Restrict the `/__provider` sub-path to an allow-list (`/api/chat`, `/api/tags`) in `provider-proxy.js:121-124`.

### 1.2 The SSRF guard can be bypassed *(major)*

> **Why it works this way —** Stopping a server from fetching an internal address on a third party's behalf means recognising every way of writing the same address — and there are many, while the guard here compares strings. An IPv4 address dressed up as IPv6, or `0.0.0.0`, resembles none of the patterns tested and yet genuinely reaches the local machine. Above all, the guard checks the address requested and not the address finally reached: since redirects are followed by default, an allowed target need only answer "look over there" for the check to collapse in a single step.

`server/provider-proxy.js:35-56`. Verified **by running** the exported function:
- `http://[::ffff:127.0.0.1]/...` **passes** — `new URL(...).hostname` is `[::ffff:7f00:1]`, and line 54 only tests `::1`/`[::1]`/`fe80`/`fc`/`fd`; a string starting with `[` matches nothing.
- `http://0.0.0.0/...` **passes** — the IPv4 regex (l.41) matches but `a === 0` falls into no branch of `isPrivate` (l.44-49).
- Both genuinely reach the loopback (fetch tested).
- The `fetch` at `provider-proxy.js:173-177` **has no `redirect` option** → undici follows 3xx by default. A `302` to `http://169.254.169.254/latest/meta-data/…` is followed and the body returned (`provider-proxy.js:246-249`).

Conversely `127.1`, `2130706433`, `0177.0.0.1` are correctly blocked (normalisation by `URL`). The same guard is shared by `server/muse/fetch/fetcher.js:79`; and `server/muse/fetch/robots.js:97` explicitly sets `redirect: 'follow'`.

**Fix** (`server/provider-proxy.js`): `redirect: 'manual'` + refuse/re-validate any 3xx; strip IPv6 brackets and reject IPv4-mapped addresses (`::ffff:*`), `::`, `0.0.0.0/8`, `100.64.0.0/10`; resolve via `dns.lookup({all:true})` and re-check every address before the call. Apply the same to `robots.js:97`.

### 1.3 `/__provider` buffers a body with no limit *(major)*

> **Why it works this way —** Accumulating a request body in memory without a bound amounts to letting the client decide how much memory the server consumes. The 25 MB limit that exists elsewhere does not apply here: it is mounted further down the chain and on a different prefix, and this handler never hands over to what follows. The point that turns slowness into an outage is that the final assembly throws its exception inside an event listener, outside any promise chain: an exception nobody catches brings down the entire Node process.

`provider-proxy.js:76-83`: `readRawBody` accumulates everything then `Buffer.concat`, with no bound. The `express.json({limit:'25mb'})` at `index.js:283` is mounted **after** (l.279) and only on `/api`; on top of that the `/__provider` handler is terminal (it never calls `next()`). An aggravating detail not caught initially: past `buffer.constants.MAX_LENGTH`, `Buffer.concat` throws **inside the `req.on('end')` listener** (l.80), outside any promise chain → **uncaught exception, process crash** (there is no `uncaughtException` handler anywhere in `server/`).

**Fix**: a byte counter + `req.destroy()` past 25 MB → 413; an `AbortController` with a deadline on the upstream fetch (l.173).

### 1.4 A global image library with no owner *(major)*

> **Why it works this way —** A multi-account application can only isolate what its data model knows how to attribute. Here an image's record stores the prompt, the seed, the dimensions and the projects, but no user identifier: there is therefore nothing to filter on, and no check placed at route level makes up for that absence without first changing the data being written. What is exposed is not trivial, since an image's prompt contains the actual brief, that is, what the client asked for.

`server/images/library.js:151-163`: the stored metadata is `{hash, prompt, negative, provider, seed, width, height, createdAt, tags, projects, favorite}` — **no user field**. `library.list()` (l.195-207) filters only on query/project/favorites/slotType, and `library.zip()` (l.261-290) re-injects prompt/negative/seed into `manifest.json`. The prompts contain the actual brief (`src/lib/muse.ts:240-250` posts `prompt: slot.prompt || slot.subject` with `project: project.id`).

**Fix**: `owner: userId` in the metadata, filtering in `list()` except for admins, refusal of `remove`/`toggleFavorite` if `meta.owner !== req.user.id`. Requires threading the user from `routes.js` down to `library.js`.

### 1.5 Rate limiting is inoperative behind a reverse proxy *(medium — but one line)*

> **Why it works this way —** A "per IP address" quota presupposes knowing the visitor's address; behind a reverse proxy, the address the server sees is the proxy's, the same one for everybody. Express knows how to read the header the proxy adds to restore the original address, but only if it is explicitly allowed to — refusing to believe it by default is the right choice, provided you then configure it. Without that the counter becomes instance-wide, and the protection turns against you: a handful of attempts is enough to stop every legitimate account from signing in.

`server/index.js:256`: `req.ip || req.socket?.remoteAddress`, and **no `app.set('trust proxy', …)` anywhere** (grep confirmed). Yet `README.md:187-199` documents Nginx with `proxy_pass`. Result: `req.ip` = 127.0.0.1 for everybody → the quota of 8 attempts/minute is **instance-wide**. 9 `/api/login` requests per minute and nobody can sign in any more.

**Fix**: `app.set('trust proxy', process.env.TRUST_PROXY || false)` before `cookieParser` (l.238-239), document it in `.env.example` and `README.md:108-115`, derive `secure` from `req.secure` rather than from `NODE_ENV` (l.301). Extend `authRateLimit` to `/api/images/generate`, `/api/muse/dossier`, `/__provider`.

### 1.6 Sessions with no server-side expiry *(medium — severity revised down)*

> **Why it works this way —** The lifetime written into a cookie is an instruction given to the browser, not a rule enforced by the server: the only binding expiry is the one checked at the moment the token is re-read, and it does not exist. The severity stays moderate because the cookie is marked `httpOnly`, so invisible to the page's JavaScript: stealing it already presupposes access to the files or to the machine. That is precisely why file permissions appear in the same finding — tokens and API keys readable by any local user make such access trivial the moment it exists.

`server/index.js:296` writes `sess.t`, `currentUser` (l.286-292) **never** reads it; the `maxAge` (l.302) is a mere instruction to the browser; there is no pruning anywhere (whereas the SSO JTIs are properly pruned at l.155-156).

**To be fixed, but this is not a way in**: the cookie is `httpOnly` (l.299), so an XSS cannot exfiltrate it — you need file/backup/machine access. And two initial claims are false: the admin→user demotion **takes effect immediately** (`currentUser` re-reads `users.json` on every request, l.291), and there is no password-change route at all.

**Fix**: in `currentUser`, reject and delete any session where `Date.now() - sess.t > MAX_AGE`; a sliding TTL; a purge at start-up modelled on `consumeJti` (l.151-163); `POST /api/logout-all` (the loop already exists at l.592). And pass `{ mode: 0o600 }` to the `writeFileSync` calls in `server/index.js:76`, `text/config.js:212`, `images/config.js:194` (0644 today: API keys and session tokens in the clear, readable by any local user).

### 1.7 CSRF: SSO login-CSRF only *(medium — severity corrected)*

> **Why it works this way —** Most requests forged from another site are already blocked here, but by accident: the server accepts JSON only, which a remote form cannot send without triggering a browser preflight that nothing satisfies. What remains is the one case that escapes both barriers, plain GET navigation, which is exactly what `SameSite=Lax` lets through, and that is how the external authentication callback sets a session. A session set by a third party is not merely stolen access: reconciliation starts immediately and pushes local content into the account the attacker chose.

**What is refuted**: "an app compromised on `*.example.com` can forge `POST /api/admin/users`" — **false**. `express.json` accepts only `application/json` (body-parser sets `req.body = {}` otherwise); a cross-site form can only send urlencoded/text-plain/multipart → 400; and real JSON triggers a CORS preflight the server never satisfies (there is no `cors` middleware anywhere in the repository).

**What remains real, and serious**: `app.get('/sso/dashy/callback')` (`index.js:393`) sets the session via `setSession` (l.423) on a **top-level GET navigation** — exactly the case SameSite=Lax lets through. The `state` check is purely client-side (`src/lib/sso.ts:81`) and **never shown**: `App.tsx:34-39` calls `setSsoError()`, but `ssoError` is only rendered inside `<AuthModal>`, which only opens if `api.me()` returns null (`App.tsx:45-46`) — and the cookie has just been set. Aggravating factor: `App.tsx:49` immediately fires `reconcileOnLogin()`, so `sync.ts:84` **pushes your entire localStorage into the attacker's account** (or l.80 overwrites your projects with theirs).

**Fix**: a `state` cookie set server-side before the redirect to Dashy and checked before `setSession` (l.423); `sameSite: 'strict'`; an `Origin`/`Sec-Fetch-Site` check against `MOCKY_ORIGIN`; make `MOCKY_ORIGIN` **mandatory** when `ssoEnabled` — otherwise `expectedAudience` (l.405-406) falls back to `req.get('host')`, which neutralises the `aud` check and opens an open redirect (`curl -H 'Host: evil.tld' …` → 302 to `http://evil.tld/`).

**Batch 1 effort: 2–3 days (1.1 + 1.2 + 1.3 = 1 day and cover 80% of the risk). Regression risk: low to medium** — 1.1 breaks the "frontend only, no account" mode should it ever come back (see batch 2).

## 3. BATCH 2 — Close the browser sandbox escapes *(RISK)*

> **Why it works this way —** Mocky runs code written by a model in your browser: the only thing separating that code from your data is the browser's isolation, and that isolation rests entirely on the exact value of one attribute. The section opens by noting that the preview iframe is correctly configured, precisely so that nobody later "improves" it by adding a flag: each absent flag is a decision, not an oversight. What follows falls into two families: a second, privileged frame that goes around that isolation entirely, and the two things the sandbox attribute does not settle — what the document may send to the network, and who may speak to it.

The main sandbox is **correct**: `src/components/Preview.tsx:425` → `sandbox="allow-scripts"` without `allow-same-origin` (verified). Opaque origin: no localStorage, no cookie, no parent DOM, no popup, no top-level navigation, no download, no form. The absent flags are exactly the right ones — **on no account add `allow-popups` or `allow-top-navigation`**.

Three holes go around it.

### 2.1 `capture.ts` raises a same-origin iframe *(critical)*

> **Why it works this way —** An iframe filled by `srcdoc` and granted `allow-same-origin` is no longer isolated: it inherits the application's origin, so the model's code reaches local storage, session cookies and the parent document exactly as Mocky itself would. Everything the preview carefully refuses is granted here for the duration of a capture. What makes the finding critical is not the duration but the trigger: the capture is started by an ordinary product action, a drag in annotation mode, not by some exotic manipulation.

`src/lib/capture.ts:152` — verified: `iframe.setAttribute('sandbox', 'allow-scripts allow-same-origin')` with `srcdoc` (l.154), which runs the model's code (l.109/114). srcdoc + `allow-same-origin` ⇒ **the iframe inherits Mocky's origin**. The comment at l.18-19 owns it ("Fine for a self-hosted tool"). Trigger: `ProjectView.tsx:247-268` → annotation mode (l.894-897) — **a normal product action, one click**.

During the capture, the LLM-generated code can read `localStorage['mocky.settings.v1']` (your provider key in the clear, `settings.ts:28,53`), call `fetch('/api/admin/users', {credentials:'same-origin'})` — the `mocky_sess` cookie is `httpOnly` but **sent automatically** — hence create an admin account, overwrite all your projects via `PUT /api/data`, and rewrite `parent.document`. The only barrier is the model's goodwill.

**Fix**: remove `allow-same-origin` and let html2canvas run **inside** the null-origin iframe — it is already loaded there (`capture.ts:122`, `/vendor/html2canvas.min.js`), and `toDataURL()` works on an opaque origin as long as the canvas is not tainted. The only real tainter is `<img src="http://origin/api/images/…">`: add `Access-Control-Allow-Origin: *` on `server/images/routes.js:91-102` and `useCORS: true` in the html2canvas options (`capture.ts:135`). Fallback if the canvas stays tainted: serve a `/capture.html` page from a second port (distinct origin, same machine) and hand the dataURL back by `postMessage`.

### 2.2 That same same-origin iframe loads JS from an unpinned CDN *(critical)*

> **Why it works this way —** A script tag pointing at a URL with neither version nor fingerprint delegates to a third party — and to whoever controls the DNS between them and you — the right to run code of their choosing, at your origin, indefinitely. That is already awkward in an isolated preview; inside the frame of the previous finding, which shares the application's origin, it is direct access to your keys and your projects. The invariant banning CDNs did exist: its test only looked at the declarative capability registry, never at the tags hard-coded in the document builder, so it went green without checking anything.

`src/lib/capture.ts:101-102`: `https://unpkg.com/@babel/standalone/babel.min.js` — **no version, no `integrity`**. `capture.ts:120` and `Preview.tsx:107`: `https://cdn.tailwindcss.com` — same. A CDN compromise (or just DNS/a proxy on your LAN) = JS execution at Mocky's origin.

A documented contradiction: `Preview.tsx:22-27` states "never a CDN", and `docs/adr/001-muse.md:69` lays down invariant **I3** ("No CDN `<script>` for JS") — but `registry.test.ts` only tests `CAPABILITIES.filter(c => c.kind === 'cdn-script')`, it **does not see** the tags hard-coded in `buildSrcDoc`. Secondary consequence: the preview **does not work offline** (Tailwind fails to load, every screen renders unstyled), contrary to what the comment claims.

**Fix**:
1. `capture.ts:101-103` → point at `/vendor/babel.min.js`, which already exists (7.29.7) and is loaded by `Preview.tsx:110`. Pure removal of the CDN fallback.
2. Vendor Tailwind Play into `public/vendor/tailwind.min.js` and point `Preview.tsx:107` **and** `capture.ts:120` at it.
3. Add to `src/lib/capabilities/registry.test.ts` a test that reads the sources of `Preview.tsx`/`capture.ts` and asserts that no `<script src="http` tag appears in them — **that is the guard rail I3 is missing**.
4. Add `html2canvas` as a devDependency (today it is in **neither** `dependencies` **nor** `devDependencies`: an orphan binary, invisible to `npm audit`), plus `public/vendor/VENDOR.md` (package + version + sha256) and an `npm run vendor:sync` script copying from `node_modules`.

### 2.3 No CSP in the preview srcDoc *(major)*

> **Why it works this way —** An iframe's sandbox governs what the document may do to its parent, not what it may do to the network: with `allow-scripts` alone, the generated code issues outbound requests, loads remote images and sends silent beacons from your IP address, on every render. Only a content security policy declares what a document may contact, and there is none. On top of that, an isolated iframe can navigate itself: the document that replaces it fills the whole device frame, inside Mocky's chrome, which makes a fake sign-in page credible.

Verified: `grep -rn "Content-Security-Policy" src/ server/ index.html` returns **nothing**. `server/index.js:241` says so explicitly in a comment. `allow-scripts` alone blocks **no** outbound request: the generated component can call `fetch(..., {mode:'no-cors'})`, `new Image().src=...`, `sendBeacon(...)` silently on every render, from your IP. And a sandboxed iframe can **navigate itself** (`location.href='https://evil/login'`): the loaded document inherits the sandbox but fills the whole frame, inside Mocky's device chrome → credible phishing (`<form>` elements are blocked, `fetch` is not).

**Fix** — a meta CSP built with `window.location.origin` in `buildSrcDoc` (`Preview.tsx:100`):
```
default-src 'none'; script-src 'unsafe-inline' blob: ${origin};
style-src 'unsafe-inline' ${origin}; img-src ${origin} data: blob:;
font-src ${origin} data:; connect-src 'none'; form-action 'none';
frame-src 'none'; base-uri 'none'
```
`connect-src 'none'` kills fetch/XHR/sendBeacon/WebSocket; `img-src` limited to the origin kills the image beacon; `frame-src 'none'` prevents the nested iframe. **`blob:` in `script-src` is indispensable** (`Preview.tsx:168-171` executes the compiled module via a Blob URL). It also renders inert the risk of "the model emits an `<img src="https://tracker/px.gif">`" — which `src/lib/muse.ts:294` explicitly permits today, and which `src/lib/lint.ts:9-15` does not detect (it only looks for "lorem ipsum").

### 2.4 The postMessage bridge is never validated *(major)*

> **Why it works this way —** `postMessage` is an open channel: anything that can obtain a reference to a window can write to it, so a message is only trustworthy if the recipient checks which window it came from. Nothing is checked here, and the frame identifier that would serve as a pass is written in the clear inside the very document it claims to protect. The consequence goes beyond a forged message: the error text received goes straight back into the repair prompt sent to the model, so a component can dictate its own instructions to the generator, billed to your API key.

- **Parent**: `Preview.tsx:358-360` checks neither `e.origin` nor `e.source`. The `frameId` (`'f' + Math.random()`, l.298) is **written in the clear inside the srcDoc** (l.119) — it is not a secret. Consequence: the generated component posts `{type:'error', message:'<arbitrary instructions>'}` and that text goes **verbatim** into the repair prompt (`generate.ts:604`, `FIX_PROMPT`) up to twice, on your API key → self-sustaining prompt injection. And `picked` (l.381) is handled **without checking that `pickMode` is active**.
- **Iframe**: `Preview.tsx:237-241` accepts any window. `parent.frames[i]` is reachable cross-origin, so a malicious screen can force **another** screen into `demo` mode with its own `links`.

**Fix** (~5 lines, all inside `Preview.tsx`): parent → `if (e.source !== iframeRef.current?.contentWindow) return` at the top of l.358 (the origin of a sandboxed srcdoc is the string `"null"`, shared: unusable); `if (!pickMode) return` before l.381 and `if (!demoLinks?.length) return` before l.382; iframe → `if (e.source !== window.parent) return` at the top of l.237; `crypto.randomUUID()` instead of `Math.random()` (l.298); truncate `d.message` to 2000 chars and wrap it inside `FIX_PROMPT` (`<runtime_error_untrusted>…</runtime_error_untrusted>`).

### 2.5 Lock the flags down with a test

> **Why it works this way —** Security that rests on the exact value of a string degrades through good intentions: someone will add a flag to make a feature work, and nothing will flag it. A test that compares the whole string, by strict equality rather than by "contains", turns the decision into a constraint checked on every run. Its main value is the comment it carries, explaining why each absent flag must stay absent — in the one place anyone wanting to change it will necessarily read.

Create `src/components/Preview.sandbox.test.ts`: read the sources of `Preview.tsx` and `capture.ts` and assert the **exact value** of the sandbox strings (strict equality, not `includes`), with a comment explaining why each absent flag must stay absent. Same shape as `registry.test.ts`. This is the mechanical counterpart of I3 applied to the sandbox.

**Batch 2 effort: 1.5–2 days. Regression risk: medium** — 2.1 may break the capture if the canvas becomes tainted; validate on a screen with a Muse image before merging.

## 4. BATCH 3 — Installation and first run *(BUG + IMPROVEMENT)*

> **Why it works this way —** Installation is the one part of the product everybody goes through, and the only one where the user still has no way of telling their own mistake from a fault in the tool. When the documentation describes a product that no longer exists, the failure looks like an application bug and ends in an uninstall. The batch is small and risk-free — documentation, Docker, start-up messages — but its effect on first impressions is out of all proportion to its cost.

The Docker path (`clone` → `docker compose up -d --build` → `:8787` → admin account → Settings → key → Test) works and requires **no file to be edited**. That is a genuine strength. But the README describes a product that no longer exists.

### 3.1 The "frontend only, no account" mode no longer exists *(critical — a doc bug that looks like an app bug)*

> **Why it works this way —** The code made the authentication modal impossible to close while no account is open, which is defensible in itself. But with no backend, the calls that would let you open such an account fail too: the modal can be neither satisfied nor dismissed, and the application ends up in a dead end whose only message is an HTTP error code. The finding is rated critical because that is precisely the path the documentation offers a beginner first.

Verified: `src/App.tsx:271-274` — the comment says literally "Unauthenticated users are not allowed to close the modal and use Mocky without an account", and `if (account) setAuthOpen(false)` makes the modal unclosable. `App.tsx:41-60`: a failing `api.me()` ⇒ `setAuthOpen(true)`. With no backend, the Vite proxy (`vite.config.ts:44-47`) fails ⇒ `me()`, `config()` **and** `register()` all fail.

This contradicts `README.md:34`, `:39` ("an **optional** tiny Node + Express backend"), `:64-69` ("**Frontend only** … `npm run dev`") and `:245`. **The first path offered to a beginner leads to a 100% stuck app with "HTTP 500" as its only message.**

**A decision to take** — I recommend **owning mandatory auth** (it is consistent with batch 1, which closes the anonymous routes):
- Delete the "Frontend only" section (`README.md:62-69`), correct `:34`, `:39`, `:245`.
- Rename `dev` to `dev:web-only` in `package.json:7`, or remove it.
- Have `AuthModal.tsx` show a dedicated message when `/api/config` is unreachable: "Mocky backend unreachable — run `npm run dev:all`".

### 3.2 The Docker image does not ship `mocky.mcp.json` *(critical)*

> **Why it works this way —** A Docker image contains only what is explicitly copied into it; the file declaring the inspiration servers is not there, and the loader treats its absence as "no server declared" rather than as an error. The result is a feature that cannot be reached inside the container, while the 300 MB of Chromium it requires are installed on every build. What makes the finding critical rather than merely annoying is the silence: the availability probe answers 200 as soon as the backend answers, so the interface advertises the feature as available.

Verified: `mocky.mcp.json` exists at the root; `Dockerfile:37-39` copies only `dist`, `server`, `public`. `server/index.js:18,23` → `ROOT_DIR = /app` → `server/muse/mcp/config.js:56-63` reads `path.join(rootDir, 'mocky.mcp.json')` and returns `{servers: []}` on ENOENT. Meanwhile `Dockerfile:32-34` installs `fetcher-mcp` + `playwright install --with-deps chromium` ("adds ~300MB"). **You pay 300 MB and several minutes of build time for an unreachable feature**, and `README.md:279-281` claims the opposite.

Worse: it is **silent**. `src/lib/muse.ts:147-152` (`museAvailable`) returns `true` as soon as `/api/mcp/status` answers 200, which `server/muse/routes.js:37-39` does even with zero servers.

**Fix**: `COPY mocky.mcp.json ./` in the runtime stage of the `Dockerfile` (next to l.37-39). And make the failure visible: `GET /api/mcp/status` returns `configured: host.status().length > 0`, `src/lib/muse.ts:147` distinguishes "no backend" from "no MCP server declared", `MusePanel.tsx:91-95` shows the right message.

### 3.3 The README's `.env` instruction passes nothing to the container *(major)*

> **Why it works this way —** Docker Compose's `.env` file exists to fill in variables inside the compose file itself, not to pass them to the container: that takes an explicit directive, `env_file` or `environment`. And since `.env` is separately excluded from the build context, the server's home-grown loader does not find it either. All three mechanisms you would think of therefore fail, and none of them says why — the only symptom is a feature that stays disabled with no explanation.

`README.md:127-133` says `cp .env.example .env` then `docker compose up -d --build`. But `docker-compose.yml:19-25` (verified) has **no `env_file:`** and interpolates no variable — the SSO lines are commented out. Compose's `.env` only serves interpolation *within* the compose file. And `.dockerignore:5` excludes `.env` from the context, so the home-grown loader at `server/index.js:37-50` finds nothing either. **Three plausible mechanisms, all failing silently.**

**Fix**: `env_file: [.env]` on the `mocky` service, or explicitly list `SSO_SHARED_SECRET: ${SSO_SHARED_SECRET:-}` and so on. And log at start-up (near `index.js:61`): `SSO: enabled` / `SSO: disabled (SSO_SHARED_SECRET or SSO_DASHY_URL missing)`.

### 3.4 No useful message at start-up *(major, 20 lines)*

> **Why it works this way —** A server that announces "started" before checking what it depends on transfers the entire cost of diagnosis to the user. The three most common failures go through no message code at all: a port already taken emits an error event nobody listens for, a frontend that was never built yields 404s for want of an `else` branch, a non-writable data directory throws outside any `try`. Twenty lines are enough because the job is not to repair these situations, only to name them as they occur.

`server/index.js:642`: `app.listen(PORT, () => console.log(…))` — **no `server.on('error')`** (grep confirmed). `index.js:628-636`: `if (fs.existsSync(dist)) {...}` — **no `else` branch**. `index.js:19`: `fs.mkdirSync(DATA_DIR)` outside any try/catch.

Three common failures with no diagnosis whatsoever: port 8787 already taken → unhandled `EADDRINUSE` (and under `dev:all`, concurrently kills Vite as well); `npm start` without `npm run build` → "Mocky backend on http://localhost:8787" then a mute 404; `server/data` not writable → a crash or opaque 500s.

**Fix**: `server.on('error', ...)` with an explicit message; `else console.warn('dist/ not found — run npm run build before npm start')`; a try/catch around the `mkdirSync` with the path in the message.

### 3.5 README commands that cannot be run on Windows *(medium — it is YOUR platform)*

> **Why it works this way —** `$(pwd)` is a substitution specific to POSIX shells, and the project path contains a space, which breaks the argument even where the substitution does work; `openssl`, for its part, is not present by default on Windows. In isolation this would be a drafting detail. What makes it worth raising is that the only two documented operational procedures — back up your data, enable SSO — are precisely those, on the platform of the only person meant to run them.

`README.md:145,148`: `-v $(pwd):/backup` → fails in cmd.exe, and under PowerShell evaluates to a path containing a space (`C:\Users\…\Claude Code\Mocky`) that breaks the `-v` argument. `README.md:321`: `openssl rand -base64 48` → `openssl` is not on the standard Windows PATH. **The README's only two ops procedures — backup and enabling SSO — are inapplicable on your machine.**

The code itself is correct on Windows (`server/muse/mcp/realClient.js:36-42` translates `npx` → `npx.cmd`, the `.env` parser splits on `/\r?\n/`).

**Fix**: PowerShell variants — `-v "${PWD}:/backup"` (the quotes are mandatory) and `node -e "console.log(require('crypto').randomBytes(48).toString('base64'))"`. Add a `.gitattributes` (`* text=auto eol=lf`): there is none.

### 3.6 The rest of the batch *(medium, all small)*

> **Why it works this way —** None of these points warrants a section of its own: they are configuration lines, a Node version to declare, an unprivileged user, a missing step in the getting-started guide. They are grouped because they share the same shape — a defect that breaks nothing as long as nothing moves, and that costs a diagnosis session the day something does move: a Node upgrade, a backup to restore, a port already busy. Handling them as a block avoids weighing them one by one against more visible work, an arbitration they would lose every time.

- **No `engines`/`.nvmrc`**: `package.json` has no `engines` field, there is no `.nvmrc`, and the README mentions Node only to describe the image. Yet vite ^5.4.11 / vitest ^4.1.10 and the global `fetch` require it. Add `"engines": {"node": ">=20.19"}`, an `.nvmrc` (`20`), and "Prerequisites: Node 20+ (or just Docker)" at the top of the Quick start.
- **A Quick start with no step 0**: `README.md:45-51` then `:85-91` never say that a blocking modal opens and that **the first account becomes admin** (`index.js:347,352-353`) — irreversible afterwards without hand-editing `users.json`. Add the step, and chain the onboarding: after `onSignedIn` (`App.tsx:276-284`), if no key is configured, route to `settings` with a banner reading "Last step: your model".
- **A fragile healthcheck**: `docker-compose.yml:28` hard-codes the port although it is configurable (l.21); `Dockerfile:56` uses `process.env.PORT||8787` but **ignores `MOCKY_PORT`**, which nevertheless takes precedence server-side (`index.js:641`). And `/api/config` tests nothing. Add a `GET /api/health` that checks `fs.accessSync(DATA_DIR, W_OK)`.
- **A non-reproducible build**: `Dockerfile:32-34` — `fetcher-mcp` with no version, `npx --yes playwright` = whatever was published last, all of it wrapped in `|| echo` which returns exit 0 come what may. Pin the versions, replace the `|| echo` with a marker readable at runtime (`touch /app/.no-chromium` checked at boot).
- **No published image**: `.github/workflows/ci.yml:24-30` runs `docker build -t mocky:ci .` "(no push)", and `git tag` returns nothing. Add a `docker/build-push-action` job → `ghcr.io/…:latest` + a version tag, and document `image: ghcr.io/…` as an alternative to `build: .` (`docker-compose.yml:12-13`). That spares you a heavy 300 MB build on every update on a NAS/Raspberry Pi.
- **Container running as root**: no `USER` directive in the Dockerfile → `users.json`, `sessions.json`, `image-library/` are owned by root in the volume (backup/restore under sudo, rootless Docker broken). `chown -R node:node /app` + `USER node`. Careful: Playwright puts Chromium in `/root/.cache/ms-playwright` → set `ENV PLAYWRIGHT_BROWSERS_PATH=/ms-playwright` **before** the install.
- **No upgrade strategy**: no `version` field in `server/data/`, even though implicit migrations exist (`liftLegacy` in `text/config.js:81-86` and `images/config.js:53-58`, `LEGACY_HISTORY_KEY` in `project.ts:62,173-190`). Write `server/data/.schema.json` at boot, copy `server/data` with a timestamp before any migration, add a **portable** `npm run backup` (in Node, without tar or docker) and an "Updating Mocky" section to the README.

**Batch 3 effort: 1.5 days (3.1→3.4 = half a day and cover the essentials). Regression risk: low.**

## 5. BATCH 4 — Design foundation *(technical prerequisite for the redesign)*

**Mechanism.** Tokens as channel-by-channel CSS variables in `:root` / `[data-theme=…]`, exposed in `tailwind.config.js`:

```js
  muted:    'rgb(var(--muted) / <alpha-value>)',
  accent:   'rgb(var(--accent) / <alpha-value>)',
  onaccent: 'rgb(var(--on-accent) / <alpha-value>)',
  danger: …, warn: …, ok: …, muse: …,
}
```
**This works in Tailwind 3.4.19 and preserves `bg-surface/60`.** Changing theme becomes a swap of 14 variables again.

**Do not migrate to Tailwind 4.** The main gain (native variables) is already available in v3; v4 forces `shadow-sm`→`shadow-xs`, `outline-none`→`outline-hidden`, changes the default ring, drops the JS config in favour of `@theme`, moves the Play CDN to `@tailwindcss/browser` — and above all **would invalidate every v3 class in the screens already generated** and the whole export chain (`src/lib/export/theme.ts`, `project.ts`, `snippets.ts`). Zero user benefit.

**Substitution order** (file by file, 109 classes → 14 tokens): ProjectView (122) → MusePanel (55) → Canvas (49) = **38% of the total**. Then an ESLint `no-restricted-syntax` rule on `-slate-`/`-indigo-` literals to prevent regression.

**Also settle in this batch**:
- A single z-index scale in `tailwind.config.js`: `{ panel:20, menu:30, overlay:40, modal:50, top:60 }`.
- A global focus rule, in the base layer, **replacing** the `outline-none` of `.input`:
  `:where(button,a,[role="button"],input,select,textarea,[tabindex]):focus-visible { outline: 2px solid rgb(var(--ring)); outline-offset: 2px }`. And remove `focus:ring-0`/`border-0` from `Welcome.tsx:81`.
- `applyTheme` moved into an inline script in `index.html` **before** the CSS (today `src/main.tsx:8` applies it after the first paint while `:root` is hard-coded dark → a dark flash on every reload in the Beige theme). A default derived from `prefers-color-scheme`, never read today.

**Batch 4 effort: 3–4 days. Regression risk: high in volume, low in severity** (it is visual, not behavioural — but it touches 20 files). Do it file by file, with before/after screenshots.

## 6. BATCH 5 — The visual redesign: the "Workbench" direction *(IMPROVEMENT)*

> **Why it works this way —** This is the only batch where automated verification proves nothing: a product whose colours were all wrong would compile and pass every test. It therefore comes after the foundation, once a change of look has become a change of values rather than a shuffle of thousands of classes, and it is reviewed screen by screen. It is also the only batch whose benefit is felt immediately, which is precisely the reason not to start with it.

### The direction, and why that one

> **Why it works this way —** A visual direction chosen out of taste can neither be argued nor defended; this one is deduced from a functional constraint. The chrome of a design tool surrounds the objects being judged, and a pronounced hue in the background shifts the perception of the colours placed on it: the current grey is blue-leaning, so the tool lies about what it is presenting. Starting from there gives a verifiable criterion for each of the three decisions that follow, instead of a preference.

Mocky is a **design** tool. Its interface must keep two promises at once, and they are in tension:

1. **It must inspire confidence in its taste.** If the chrome is ugly, nobody believes the mockups it produces.
2. **It must disappear.** The canvas shows colourful mockups side by side. Every bit of colour the chrome contributes **distorts the perception** of what the user is judging.

That tension is what decides, and it disqualifies the current state: **slate is a blue-leaning grey** (`#64748b` has a markedly cool cast). A beige mockup placed on a slate background looks more yellow than it is; a blue mockup looks flat. Today the chrome lies about the colours it presents. That is disqualifying for a design tool, and it is a technical argument, not a preference.

**The chosen direction: "Workbench" (« Établi »).** The chrome is a neutral work surface; the mockups are the objects laid on it. Three decisions:

**A. A chromatically neutral grey, not slate.** Move from `slate` (blue-leaning) to `neutral`/`zinc` (desaturated) as the base family. Surfaces are distinguished by **elevation** (3 levels: `sunken` = the canvas, `surface` = the panels, `raised` = popovers/modals) rather than by borders everywhere — today `border-slate-700` appears 51 times, which hatches the interface. One shadow per level, one separating rule (`--line`), the rest by elevation.

**B. Two themes only, not three.** Today: `sombre` (dark), `light` (beige) and `logo` (teal-green), and they are inconsistent with each other — `logo` remaps indigo→teal, `light` remaps no indigo at all, so **the same buttons are teal in one theme and indigo in the other**. Keep **`sombre` (default) + `clair` (light)**, and make the logo's teal **the single accent of both**. You lose a decorative theme, you gain an identity. The beige of `light` (`#e9e0cd`) is too warm and too saturated for a canvas background — it tints everything laid on it; replace it with a very slightly warm paper white (`#faf9f7`) that keeps the "paper" feel without distorting colours.

**C. One accent, saturated, and rare.** The logo's teal, used **only** for the primary action and the active state. The semantic colours (danger / warn / ok) desaturated one step relative to the Tailwind defaults, so that they never shout louder than a mockup. And **Muse's fuchsia kept** as the only non-accent colour: it is already the feature's visual signal, it is recognisable, it costs nothing.

**Typography.** Today the whole product is at 12 px or below — which produces an "internal-tool prototype" feel and rules out comfortable reading. Move to a **6-step** scale, defined in `tailwind.config.js`, with arbitrary sizes forbidden:

| Step | Size | Use |
|---|---|---|
| `caption` | 11 px | non-essential badges **only** |
| `body-sm` | 13 px | control labels, toolbar |
| `body` | 14 px | **running text — the new default** |
| `lead` | 16 px | intro, prompt field |
| `h3` | 20 px | panel and modal titles |
| `h2` | 28 px | page titles |

One pairing only: `Inter` (or the current system stack, which is fine) for the UI, `ui-monospace`/`JetBrains Mono` for code **and numeric values** (zoom, dimensions, hashes) — that detail is what says "precision instrument".

**Density and shapes.** 3 radii only (`sm` controls / `md` cards and fields / `lg` surfaces and modals), the other 3 removed. A minimum height of **32 px** on every click target via the `Button` component — today `AccentPill` is 16×16 px (`DesignPanel.tsx:453`) and **the DESIGN.md page shows 238 of them** (17 presets × 14 pills), which is both impossible to hit on a trackpad and visually saturated on the single most important screen for the product's brand positioning. **Restructure that page so the variants only show for the selected preset: 238 pills → 14.**

**The canvas is the stage.** The toolbar becomes a single floating `raised` surface, with a `Segmented` control for the exclusive modes (Link / Modify / Interact / Annotate) instead of 4 independent buttons — which **also fixes bug 5.2 below**. The loading and error states move out of the transformed layer (see 5.3).

### Layout bugs to fix in this batch

> **Why it works this way —** These three defects are not one-off oversights but consequences of the way the layout is built: a hard-coded height instead of a grid, five independent booleans instead of a single mode, overlays placed inside the layer that zoom scales. Fixing them separately would mean doing the same work twice, since rebuilding the layout makes them disappear by itself. They are therefore attached to this batch rather than to the bug batch.

**5.1 — The magic number `57px`, duplicated and wrong.** `Welcome.tsx:66` (`min-h-[calc(100vh-57px)]`) and `ProjectView.tsx:855` (`h-[calc(100vh-57px)]`) whereas the header measures **61 px** (`App.tsx:102-103`: `py-3` = 24 px + logo `h-9` = 36 px + 1 px of `border-b`). The canvas overshoots the viewport by ~4 px and makes the whole page scroll, which shifts the floating toolbar and the composer. **Fix:** `<div className="grid grid-rows-[auto_1fr] h-dvh">` — header at `auto`, work area at `1fr`. The magic number disappears. `dvh` rather than `vh`.

**5.2 — Two floating panels exactly on top of each other.** The Links panel (`ProjectView.tsx:917`) and `DesignSystemPanel.tsx:42` are both at `absolute right-4 top-11`, with no z-index. Activating "🔗 Link" does not deactivate `showSystem` and vice versa → both can be open and overlap pixel for pixel. **Fix:** a single `mode: 'select'|'link'|'modify'|'annotate'` state + a `rightPanel: 'none'|'links'|'system'` state, instead of 5 independent booleans. The "deactivate the other two modes" logic is currently **copied out three times identically** (`ProjectView.tsx:991-995`, `1005-1010`, `1030-1035`).

**5.3 — Loading/error states are rendered at canvas scale.** `Canvas.tsx:383` computes `inv = 1/view.scale` and conscientiously applies it to its own labels (l.431, 464, 481, 599, 682), but **not to the overlays in `Preview.tsx:431-447`**, which sit in the layer transformed by `scale(view.scale)`. The initial zoom is **0.4** (`Canvas.tsx:134`), and `fitAll` can go down to 0.05. So "Generating…" renders at **4.8 px** and the runtime error message at **5.6 px** — illegible. Yet that is exactly the information the user needs in order to rephrase their prompt. **Fix:** move those overlays out of the transformed layer and render them in screen coordinates above the frame; surface render errors in a `Banner` in the composer with a "Fix" button; add a real `Skeleton` (title + 3 lines + card, shimmer respecting `prefers-reduced-motion`) instead of the empty white rectangle.

**Batch 5 effort: 4–6 days. Regression risk: low functionally, high visually.** This is the only batch where "it compiles" proves nothing — plan a screen-by-screen review pass.

## 7. BATCH 6 — Accessibility, keyboard, responsive, language *(BUG + IMPROVEMENT)*

> **Why it works this way —** The four topics in this batch share one property: they are invisible to someone developing with a mouse, on a large screen, in the language they write themselves. They are therefore never discovered through use, only by deliberate census — hence findings expressed in counts of occurrences rather than in impressions. The batch is placed after the redesign because the modals and the toolbar are being rewritten there anyway: adding the roles, the shortcuts and the breakpoints at the same moment avoids doing the work twice.

### 6.1 The Space key is broken across the whole application *(critical, 5 lines)*

> **Why it works this way —** A keyboard listener attached to `window` does not receive only the keys meant for the component that installed it: it receives them all, whatever element has focus. Since the canvas stays mounted underneath every surface opened on top of it, its panning shortcut cancels the Space key everywhere, and Space is a checkbox's only activation key. The defect is invisible with a mouse, which explains how it coexists with keyboard navigation that otherwise works: you can reach a button, but not operate it.

`src/components/Canvas.tsx:196-214`: the handler is attached to **`window`** and calls `e.preventDefault()` as soon as `e.code === 'Space' && !isField(e.target)`; `isField` (l.197-198) exempts only `INPUT` and `TEXTAREA`. But as soon as a project contains a screen, Canvas is permanently mounted (`ProjectView.tsx:857`) and sits under **every** surface opened above it: toolbar, context menu, Modify/Link modals, code viewer, Bibliothèque (the image library), Lightbox.

Consequence: **you can tab to a button but not activate it.** The Bibliothèque's checkboxes (`Bibliotheque.tsx:141,145`) can no longer be ticked **at all**, Space being their only activation key. Keyboard navigation on the main screen is completely blocked, invisibly to a mouse user and therefore never detected.

**Fix:** attach the listener to `containerRef` (`Canvas.tsx:388`) with `tabIndex={0}` rather than to `window`; or extend `isField` to `t.closest('button, a, select, [role="button"], [contenteditable], input, textarea')` and only `preventDefault()` if `document.activeElement === containerRef.current || document.body`. Check while you are there: `onWheel` (`Canvas.tsx:341`) does not `preventDefault`, so Ctrl+wheel zooms the canvas **and** the browser simultaneously.

### 6.2 The canvas is 100% mouse-driven *(major)*

> **Why it works this way —** A `div` with pointer handlers is not a control: the browser grants it neither focus, nor keyboard behaviour, nor a role announceable to assistive technology. None of the canvas's core operations — select, move, rename, delete — therefore has a keyboard equivalent, and a screen's action buttons only appear after a click. This is not solely an accessibility matter: it is also what deprives everybody of arrow keys for pixel alignment and of the Delete key.

`Canvas.tsx:409-421`: each screen is a `<div>` with `onPointerDown`/`onContextMenu`, no `tabIndex`, no `role`, no keyboard handler. Exhaustive search: `tabIndex` appears only once in all of `src/components` (`DesignPanel.tsx:108`), and **no** `Delete`, `Backspace` or `Arrow*` key is handled anywhere. A screen's action buttons (`Canvas.tsx:467-483`) only appear after mouse selection.

No core operation — select, move, resize, rename, delete, open the menu — is reachable from the keyboard. And it is also an ergonomic gap **for everybody**: no Delete, no arrow keys for pixel alignment, no Ctrl+D.

**Fix:** a focusable container (`tabIndex={0}`, `role="application"`, `aria-label`) with arrows = move by 1 px (Shift = 10), Delete = delete, Enter = rename, Esc = deselect, Ctrl+A, +/- = zoom, 0 = fit. Each frame at `tabIndex={0}` + `role="button"` + `aria-label={s.name}` + `aria-selected`. Actions visible on `:focus-within` too. A shortcuts help panel ("?") — the current hint (`Canvas.tsx:747`) mentions only the mouse.

### 6.3 The 8 modals have neither role nor focus trap *(major — solved by `src/ui/Modal.tsx` from batch 4)*

> **Why it works this way —** A modal is a promise: "nothing else is reachable while I am here". Visually, a scrim is enough to keep it; to the keyboard and the screen reader, it only exists if it is declared (`role`, `aria-modal`) and enforced (focus trapped, restored on close, Esc closing), failing which focus wanders behind the scrim, into controls the user cannot see. Eight hand-rolled modals are eight chances to forget one of those pieces: that is why the fix is a single component and not eight corrections.

Exhaustive search: `aria-` appears **only once** in `src/components` (`Preview.tsx:224`, in code injected into the iframe), and `role=` **only once** (`DesignPanel.tsx:107`). None of the 8 modals has `role="dialog"`, `aria-modal`, `aria-labelledby`, a focus trap or focus restoration. Esc is missing on `pendingLink` (`ProjectView.tsx:1271`, absent from the list at l.156-167) and on `AuthModal`.

A special case: `AuthModal` cannot be dismissed by clicking the scrim when the user is not signed in (`App.tsx:271-275` silently ignores `onClose`) — the click does nothing and **nothing explains it**. Fix: do not wire `onClick` on the scrim at all, and display "An account is required to use Mocky".

Heading hierarchy: `<h1>Mocky` (`App.tsx:107`) is the only heading on the project route, the modals jump straight to `<h3>` (`ProjectView.tsx:1280,1324`), and `DesignSystemPanel.tsx:44` + the Links panel (`ProjectView.tsx:919`) title themselves with `<span>` elements.

### 6.4 Invisible focusable controls *(medium)*

> **Why it works this way —** `opacity-0` hides a button from the eye without removing it from either the tab order or the reach of a click: it stays perfectly operable, merely invisible. A keyboard user can therefore trigger a permanent deletion without having seen what they activated, and on a touchscreen — where hover does not exist — the same button becomes unreachable instead. The problem is not making a rarely used action discreet, it is making its existence depend on a state, hover, that not every input mode can produce.

6 places where a real `<button>` is rendered as `opacity-0 group-hover:opacity-100` with no focus variant: `Bibliotheque.tsx:205` (favourite/download/**delete** an image), `:221`, `ProjectsHome.tsx:90` (**delete a project**), `DesignPanel.tsx:128`, `MusePanel.tsx:71` and `:248`, `ProjectView.tsx:1134`. A keyboard user tabs into the void and can trigger a **permanent deletion** without ever seeing the button; on touch they are simply unreachable.

**Fix:** add `group-focus-within:opacity-100 focus-visible:opacity-100` and `[@media(hover:none)]:opacity-100`. Better still: in the redesign, stop hiding destructive actions behind hover — a permanent opacity of 0.5 rising to 1 on hover/focus.

### 6.5 Responsive support is all but non-existent *(major)*

> **Why it works this way —** A toolbar built as a plain flex row, with no wrapping, no maximum width and no overflow handling, has an incompressible width: below that threshold its last buttons leave the screen and the page starts scrolling horizontally, which in turn shifts everything positioned absolutely. The question is not whether Mocky should fit on a phone: it is a desktop tool, and owning that is a valid answer. The problem is that today it owns nothing — it breaks, without saying so, on a merely narrowed window.

A full census of `sm:`/`md:`/`lg:`/`xl:` prefixes in `src/`: **12 occurrences** (Bibliotheque 5, Welcome 2, ProjectsHome 2, MusePanel 2, DemoPlayer 1). **Zero** in App.tsx, ProjectView.tsx, Canvas.tsx, AdminPanel.tsx, SettingsPanel.tsx, DesignPanel.tsx, AuthModal.tsx, DesignSystemPanel.tsx.

The toolbar (`ProjectView.tsx:979`) is a `flex items-center gap-1` **with no `flex-wrap`, no `max-w`, no `overflow-x`**, holding 9 text+emoji buttons + 2 separators ≈ 700-730 px incompressible, at `absolute left-4` inside a parent with no `overflow-hidden`. **Below ~750 px, Demo and Export leave the screen** and the body scrolls horizontally.

**Fix:** take a clear position — Mocky is a desktop tool, but it must degrade cleanly. A single `Segmented` for Link/Modify/Interact/Annotate (already planned in batch 5), a "⋯" menu below `md` for Frame/System/Demo/Export, `flex-wrap` + `max-w-[calc(100%-2rem)]` as a safety net, `overflow-x-hidden` on `ProjectView.tsx:855`, and an explicit fallback screen below 640 px ("Mocky needs a wider screen") rather than a broken interface.

### 6.6 The UI is bilingual **inside the same components** *(medium — but it is the most visible signal)*

> **Why it works this way —** Two languages in the same row of buttons are read before anything else: the interface announces unfinished work, whatever the quality of what it produces. To that is added a mechanical consequence — the document's language attribute declares only one of them, so a screen reader pronounces the French using English phonetic rules, which makes it incomprehensible. The only durable fix is to lift the strings out of the components, which explains the timing: the redesign already reopens every one of them.

A verified inventory. **French**: `Bibliotheque.tsx`, `MusePanel.tsx`, `ImageProviderSettings.tsx`, `TextProviderSettings.tsx`, `ImageLightbox.tsx`. **English**: `App.tsx`, `Welcome.tsx`, `ProjectsHome.tsx`, `AdminPanel.tsx`, `AuthModal.tsx`, `DesignPanel.tsx`, `DesignSystemPanel.tsx`, `DemoPlayer.tsx`, `CodeView.tsx`, `PresetPicker.tsx`, `Preview.tsx`, `ProjectView.tsx`. **Mixed within a single component**: `Canvas.tsx` — the **same action bar** shows "Rename" (l.467), « Voir le prompt qui a créé cet écran » (l.470), "More options (or right-click the screen)" (l.475), "Delete screen" (l.483). `SettingsPanel.tsx` is in English except for the banner at l.112-120.

And `index.html:2` says `<html lang="en">` — so a screen reader pronounces all the French with English phonetic rules.

**Fix:** choose **French** as the default (the newest and best-documented screens — Muse, Bibliothèque, providers — already are). Extract into `src/i18n/fr.ts` + `src/i18n/en.ts` with a minimal typed `t()` (a Map plus a 15-line hook; **no need for i18next** for ~400 strings). Now is the right moment: the redesign already touches every component. `index.html:2` → `lang="fr"`, driven by the chosen language. **An immediate correction even without i18n:** `Canvas.tsx:467-514` and `SettingsPanel.tsx:112-120`.

**Batch 6 effort: 3–4 days (6.1 = 30 minutes and unblocks all keyboard navigation). Regression risk: low.**

## 8. BATCH 7 — Features *(IMPROVEMENTS + NEW)*

Missing: "no TypeScript annotations" (l.14), "no imports" (l.15), "exactly one App component" (l.16), the sentinel protocol (l.9-11). **7.5 — Capability selection via a naive `includes()`** *(medium, effort S)*. `src/lib/capabilities/select.ts:26`: `allTriggers.some(kw => text.includes(kw.toLowerCase()))` — substring matching, no word boundary, over the prompt **plus the Muse dossier** (`ProjectView.tsx:504`). ### 8.5 — npm audit: do NOT run `audit fix --force`

> **Why it works this way —** A dependency audit counts published advisories, not paths actually reachable in your deployment: here the majority of the serious alerts target the development server, which never runs in production since Express serves already-built files there. `--force` also accepts major version bumps along the way, that is, it trades a certain build regression for vulnerabilities that do not apply. The real cost of the command is not the breakage: it is that a counter back at zero makes the one vulnerability that does concern production disappear from view.

Full `npm audit`: 8 vulnerabilities (4 high). `npm audit --omit=dev`: **3 only**. Meanwhile the one genuine production vulnerability goes unnoticed.

→ **Patch-level fixes only, no breakage:**
```
npm i -D postcss@8.5.25 concurrently@9.2.4
npm i @modelcontextprotocol/sdk@1.30.0     # the only PRODUCTION vulnerability
npm update body-parser                      # 1.20.6 via express
```
That brings the audit down to the single vite/esbuild line — to be accepted and documented (the dev server only listens on localhost). Later, vite@7; **not vite@8**.

## Annex — corrections made to this audit during implementation

> **Why it works this way —** An audit is a set of hypotheses verified by reading; implementation is the only real test, and it disproved two of them. The false claims are left as they stand in the body of the document and corrected here rather than rewritten in place, because what is useful is not the conclusion but the reasoning that led to the error: re-reading it is what stops you repeating it. A separate annex also draws a clear line between what was measured and what was inferred.

Two claims in the report above turned out to be false when implemented.
They are kept as they stand in the body of the document, and corrected here.

### §2.1 — the fix proposed for `capture.ts` does not work

> **Why it works this way —** A security decision can be right on paper and wrong in the browser: the initial reasoning concerned the capture frame alone, and ignored what a rendering library does inside it, namely create documents of its own. Since isolation is passed on to each of them with a fresh origin every time, what the frame loses is not access to the application but access to its own working copy — so the capture does not degrade, it stops. This is the kind of error no code review reveals, only execution, which is what justifies correcting the report rather than rewriting it.

The report claimed it was enough to remove `allow-same-origin` and
"let html2canvas run inside the null-origin iframe", the only risk being
a canvas tainted by a remote image.

**That is false, and verified by measurement.** html2canvas clones the document into
an iframe it creates itself; but sandbox attributes propagate to
descendants, and without `allow-same-origin` each descendant receives a **fresh**
opaque origin. The frame therefore cannot read its own clone:

```
Blocked a frame with origin "null" from accessing a cross-origin frame.
```

The same failure with `foreignObjectRendering: true` — html2canvas goes through the
cloning iframe in both modes. A hand-written SVG `<foreignObject>` route
does work on an opaque origin (`toDataURL` succeeds, canvas not tainted), but
it carries neither the Tailwind stylesheet nor the images: that would mean
rewriting html2canvas.

`allow-same-origin` is therefore **kept**, and documented as a known limitation
in `src/lib/capture.ts` and in `tests/preview-sandbox.test.js`. What was
closed instead: the bundles are vendored and pinned by checksum (Babel
came from an unpkg URL **with no version**, loaded directly into that privileged
frame), and a CSP forbids `connect-src`, `form-action`, `frame-src`,
`object-src`, `base-uri` and restricts `img-src` to the origin — the frame no longer has
any network channel to get out whatever it might read.

The real fix remains **origin separation**: serving the capture
shell from a distinct origin (a second port, or a sibling hostname) while
keeping `allow-same-origin`. html2canvas then works, and the frame is
cross-origin with respect to the application.

### §2.3 — `script-src 'self'` would have blocked everything

> **Why it works this way —** A content security policy is reasoned from the origin of the document that carries it, and that is precisely what the report assumed without checking: the preview document has no named origin, since it is isolated, so the keyword meaning "myself" no longer corresponds to any address. Written that way, the directive would have allowed no script at all and would have switched off every preview instead of protecting them. The lesson goes beyond this case: a policy copied from memory assumes an ordinary origin context, and that context does not exist inside an isolated frame.

The proposed CSP used `'self'`. In a sandboxed document without
`allow-same-origin`, the origin is opaque and `'self'` serialises to `"null"`:
the directive would have covered none of the vendored scripts, and **every
preview would have stopped working**. The parent's origin must be named
explicitly (`window.location.origin`), which is what `cspMeta()` does in
`Preview.tsx`.

Verified under real conditions: React, ReactDOM, Babel and Tailwind load,
Babel compiles, the Blob script runs, the component renders, Tailwind applies
`rgb(16, 185, 129)` for `bg-emerald-500` — and `fetch()` is blocked by
`connect-src 'none'`.
